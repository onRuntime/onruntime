我们喜欢保持一个干净的项目历史。我们的提交规范受到 [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0) 的启发，并结合 [gitmoji](https://gitmoji.dev) 进行了定制，这样更具视觉效果和趣味性。

## 结构

提交信息应按照以下结构编写并**使用小写**：

```
<gitmoji> <type> <description> [(#<issue number>)]

[可选的主体]

[可选的附注]
```

### 示例

```bash
📝 更新文档贡献者

- 添加 @jerembdn 作为贡献者
- 添加 @younesbessa 作为贡献者

共同作者：Younes Bessa <younes@onruntime.com>
```

大多数情况下，一个简单的一行就足够了：

```bash
📝 更新文档贡献者
```

## 类型

我们使用以下提交类型：

| 类型 | 描述 |
| --- | --- |
| `add` | 添加新功能 |
| `fix` | 修复一个bug |
| `improve` | 改进某个东西 |
| `update` | 更新某个东西 |
| `remove` | 移除某个东西 |
| `refactor` | 重构某个东西 |
| `rename` | 重命名某个东西 |
| `move` | 移动文件或文件夹 |
| `upgrade` | 升级依赖 |
| `downgrade` | 降级依赖 |
| `initial` | 一个仓库的初始提交 |
| `release` | 发布 / 版本标签 |

仓库的第一次提交使用 `initial`，版本标签使用 `release`：

```bash
🎉 初始提交
🔖 发布 @onruntime/translations v0.3.0
```

## 描述

用**命令语气**和**小写**写描述：

```bash
# 好
📝 更新文档贡献者

# 不好
📝 更新了文档贡献者

# 不好
📝 Update documentation contributors
```

## 问题编号

通过添加问题编号将提交链接到问题：

```bash
📝 更新文档贡献者 (#123)
```

## 主体

使用主体提供上下文和动机：

```bash
📝 更新文档贡献者

- 添加 @jerembdn 作为贡献者
- 添加 @younesbessa 作为贡献者

共同作者：Younes Bessa <younes@onruntime.com>
```

<Callout type="info" title="一个提交，一个目的">
  每个提交应代表一个单一的逻辑变化。不要混合无关的更改。
</Callout>
